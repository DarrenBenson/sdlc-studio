The engagement floor takes a schema v3 id as its `engagement_floor.adopt_after` cutoff
(`BG-01KXB3QF`) where it raised `ValueError` and told you to set a sequential one. It reads the
cutoff and compares it as `conformance.adopt_after` does: an id minted in an earlier timestamp
bucket, and the cutoff id itself, are grandfathered; another id in the cutoff's bucket and every
later one are judged; on a migrated project the sequential ids are grandfathered under it. A v3
cutoff in a bucket the clock has not reached is refused as a forward disarm, as a numeric cutoff
above the highest existing id already is. A numeric cutoff judges exactly as before, and the
printed remedy names a v3 id as a legal cutoff beside the bare and prefixed sequential ones.

Where a cutoff is no id at all, the refusal now names the v3 form among those accepted, for the
floor and for `conformance.adopt_after`, which also take one; a caller that takes no v3 id
gives the refusal it gave before. `migrate.py` no longer says no cutoff can reach a unit with a
v3 id: it says a numeric cutoff cannot, and that a v3 cutoff can but also exempts every
sequential id and, within its own timestamp bucket, only itself.
