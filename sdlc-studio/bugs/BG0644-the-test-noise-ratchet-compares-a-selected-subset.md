# BG0644: the test-noise ratchet compares a selected subset against a whole-suite baseline

> **Status:** Fixed
> **Verification depth:** functional
> **Severity:** Medium
> **Points:** 5
> **Affects:** tools/skill-tests.sh, tools/test_noise.py, tools/test-noise-baseline.json, tools/tests/test_test_noise.py, sdlc-studio/tsd.md
> **Created:** 2026-09-03
> **Created-by:** sdlc-studio file
> **Raised-by:** sdlc-studio; agent; v1
> **Raised-in-batch:** none open - raised outside a delivery batch

## Summary

The test-noise ratchet is an absolute count checked against a SELECTED subset, so a commit that adds leaks passes the gate it is supposed to fail. tools/skill-tests.sh says of its baseline: "Frozen here, the gate fails the moment a change adds one." That is true only of a full run. The commit-msg hook passes a selection (.githooks/commit-msg:268), the check is `count <= baseline` over whatever that subset printed, and a subset almost always prints fewer than 119 lines whatever it added.

## Steps to Reproduce

Commit 8f808b0c..9260c513 added two shipped warnings - `file_finding.report_unverifiable_criteria` (BG0636) and `critic`'s unreadable-closure report (BG0631). They leak 37 lines across 24 uncaptured call sites in ten test modules. Every one of those commits passed the pre-commit and commit-msg gates, because each selected subset stayed under 119. The full run in CI printed 142 against the baseline of 119 and failed - after the push, with nobody reading it (BG0642). Reproduce with: `bash tools/skill-tests.sh test_file_finding.py` (green, leaks 13) then `bash tools/skill-tests.sh` (red at 142).

## Proposed Fix

Make the ratchet measure what the run can be held to. Either scale the baseline to the selection (a per-module leak budget summed over the selected set), or compare against the SAME selection at the base ref so the check is a delta rather than an absolute. A per-module budget is the honest shape: it is the only one under which a subset that adds a leak cannot pass.

Groomed 2026-09-04: the budget moves from the `TEST_NOISE_BASELINE=106` scalar in `tools/skill-tests.sh` to `tools/test-noise-baseline.json`, one entry per test module, summing to the measured 106. `test_noise.py` takes the selection and holds each selected module to its own entry and the run to their sum; a full run's sum is the old total. The comment in the script then states a guarantee the selected path can keep. The `--baseline` scalar stays as an override for a consuming project with no budget file. The shrink-only rule is numeric (a count may fall, never rise), which the set-based reader in `test_baselines_only_shrink.py` cannot express, so it lives in `test_noise.py` as `budget-check` against `git show HEAD:` and is exercised on a fixture repository.

Plan review round 1 (2026-09-04) settled three things. Attribution is by SUM over the selection, because one `unittest` process gives no per-module attribution and running per module would change the selected path's shape and cost; the criterion says so and the masking bound is stated. The full-run ceiling is a separate `_total` entry (106, measured) rather than the sum, so day one does not refuse on an apportioning mismatch. `budget-check` is CALLED - by the script before the suite and by a tools test over the real tree - because a shrink rule exercised only on a fixture is a mechanism that reaches no caller (carried lesson 1). The file takes precedence over the `TEST_NOISE_BASELINE` scalar; the scalar remains only as the fallback when no budget file is found. The earlier "consuming project" reason for keeping it was wrong: `tools/` ships nowhere. Points 3 to 5.

Plan review round 2 (2026-09-04): the zero-hold promise contradicted AC1's own masking bound, so AC3 now says an unrecorded module CONTRIBUTES ZERO and exercises it selected alone with the fixture numbers that separate the max-defaulting mutant from the correct code. The scalar fall-back re-admitted the absolute check whenever the file was unreadable, so it is gone from the script: a missing or unreadable budget file refuses loudly. `sdlc-studio/tsd.md` states the number is held in `TEST_NOISE_BASELINE` and is in Affects to say where it is held now. Measuring the per-module entries (each module run alone, about forty of them) is inside the 5 points. The script records nothing to `.local` itself (the timing records are in commit-msg), so a test driving it leaves the repo-writes lane clean.
