## Summary

`closures_from_document` claims structured input needs no delimiter, so nothing a reviewer writes can be read as one - but it serialises each item back to `<finding> -> <evidence>` text and escapes only the semicolon, and `parse_closures` then splits at the FIRST `->`. A finding whose own text contains `->` (a reviewer writing a status transition, `Fixed->Verified`) is cut at that arrow. The closure then carries only the text before it; when that is shorter than the 24-character prefix minimum, or the finding belongs to a non-standing rejection (where ordinals are refused), no closure can name it. The repair stays PARTIAL for ever and `_test_plan_gate` refuses In Progress on a unit whose repaired plan an independent seat has APPROVED. Hit on US0627 in RUN-01M2JA6J: its round-1 REJECT raised `AC2 - Fixed->Verified and Fixed->Closed on a bug already at Fixed are unpinned`.

## Steps to Reproduce

1. Record a plan-review REJECT on a unit whose ISSUES include a finding beginning `AC2 - Fixed->Verified and ...`, then a second REJECT under a different brief, then an APPROVE.
2. Write a --closed-file JSON naming every raised finding by its exact text.
3. Run `critic.py repair --unit <id> --phase plan-review --closed-file <doc>`.
4. It refuses: closure 'AC2 - Fixed' names no finding. Quoting the text after the arrow is not a prefix; `#n` is scoped to the standing verdict, so the round-1 finding cannot be named at all.

## Proposed Fix

Both halves, because the stored row is text and must read back to what was written.

1. **No text round trip on the JSON path.** `cmd_repair`'s `--closed-file` branch hands `record_repair` the list of `{finding, evidence}` objects, and `record_repair` accepts that list or the flag's text. A structured finding is never re-split, and its disposition is read from the evidence exactly as written.
2. **One new escape in the stored row.** The row serialiser writes every `->` inside a FINDING as `-\>`, after doubling `\` and escaping `;` as today. Evidence arrows stay bare: the reader splits at the first unescaped arrow, so everything after it is evidence already. `parse_closures`, and `unreadable_closures` with it so the write and read paths cannot disagree, scan the raw item with `\\`, `\;` and `\>` recognised, split at the first `->` whose `>` is not escaped, then unescape. The escape is scoped to the closure channel; `parse_findings` is unchanged.
3. **Legacy rows parse as today.** A `\>` pair occurs in no stored row (0 of the 336 rows in `sdlc-studio/reviews/repair-record.md`, 0 across `sdlc-studio/reviews/*.md`, measured at 79c62ec0), because today's writer doubles every backslash. A doubled backslash before `>` (`-\\>`) still reads as the literal `-\>`, never as an escaped arrow.
4. **The `--closed` flag accepts the same escape.** A typed `Fixed-\>Verified` is an arrow inside the finding, not the separator, as `\;` already is a literal semicolon there. A bare arrow inside a typed finding cannot be told from the separator, so when the fragment before it names no raised finding, the refusal names the `-\>` escape and `--closed-file`.
5. **The text path refuses a finding cut at its own arrow.** Whether the text after a bare arrow "parses as evidence" is not decidable - any text is evidence. What is decidable is the raised text: when the fragment before the first bare arrow resolves only by PREFIX to a raised finding whose own text continues with `->` at exactly that point, and the item carries a further bare arrow, the arrow was the finding's, and the closure is refused naming `-\>` and `--closed-file` before any row is written. An evidence arrow after a finding that does not continue with one is never refused (84 of 2765 stored closure items carry more than one arrow, measured at 6fd766cc).
6. **The list branch keeps both write-path guards.** Structured closures reach `record_repair` with their `ids` computed from the evidence and their shape checked (empty `finding` or `evidence` refused), as the text round trip did; the reroute moves both off `parse_closures` and `closures_from_document`.

Implementer trap: on a fixture whose two REJECTs share a date, `repair_state` reads each closure once per rejection (2 closures read back as 4, fixed=4, at 79c62ec0; pre-existing, no bug filed). Tests assert state, outstanding membership and per-closure fields, never the `fixed` or `filed` counts.

`-\>` renders as `->` in markdown, so the ledger still reads naturally, and `_clean` rewrites only `_`, `|` and newlines, so it does not interact with the escape.
