## Summary

AGENTS.md states that `release-rehearsal` and `revert-check` bind at the push and release boundaries, and `gate.py --boundary push` exists to run them. Nothing invokes it. There is no `.githooks/pre-push` and none in `.git/hooks/`, and `core.hooksPath` points at `.githooks`, so a push runs no gate at all - it completes in seconds. Both lanes are therefore documented as binding at a boundary that has no hook behind it, which is the rule-with-no-gate shape AGENTS.md itself names as the weakest available fix.

## Steps to Reproduce

1. `git config core.hooksPath` reports `.githooks`.
2. `ls .githooks/pre-push` and `ls .git/hooks/pre-push` both report no such file.
3. `git push origin main` completes in seconds with no gate output.
4. AGENTS.md's own roster says release-rehearsal and revert-check bind at `push|release`.

## Proposed Fix

Add `.githooks/pre-push` invoking `gate.py --boundary push`, and have `tools/enable-hooks.sh` install and name it beside the other two. Then pin the roster the way `check_spec_claims` already pins the pre-commit lanes: a test that reads AGENTS.md's boundary claims and asserts a hook exists for each named boundary, so the next lane documented at a boundary cannot be documented into a hook nobody wrote.

Groomed 2026-09-04: measured at HEAD, NOTHING invokes `--boundary release` either - not `release.yml`, not `release_cut.py`, not the release-gate template. The one hook covers both: a branch ref is the push boundary, a tag ref is the release boundary, read from the refs git hands pre-push on stdin. The tests live in `tools/tests/` because the hooks are repo-only; `test_gate.py` is dropped from Affects for that reason. The roster guard is a small checker, `tools/boundary_roster.py` (AGENTS.md roster in, hooks directory in, missing boundaries out), so its control has a production change to die on; it is exercised over the real tree by the tool-tests lane rather than added as a pre-commit lane to a gate already over budget.

Plan review round 1 (2026-09-04) - the cost is the finding. `gate.py --boundary push` runs the FULL suite (601-648 s over the last ten samples in `.local/gate-timings.json`) plus `release-rehearsal` and `revert-check`, so a push that completes in seconds will take ten to fifteen minutes. AGENTS.md's own law is that a guard whose cost is paid every time gets switched off. The hook therefore announces its cost before paying it (AC4), the bypass is named in every refusal, BG0642's CI read happens BEFORE the gate so a red main refuses in a second, and the per-push price is put to the operator at sign-off as a decision rather than discovered on the first push. The stub is placed at the path the hook invokes, as the existing hook fixtures do, because a PATH stub cannot reach `python3 "$skill/gate.py"`. Points 3 to 5: a hook that parses stdin and selects two boundaries, a checker, an eight-test module that builds clones and remotes, and two documents.

Plan review round 2 (2026-09-04): three findings were executed against the tree. `gate_timing.py estimate` prints NOTHING with no history and no boundary key has ever been recorded, so AC4 now names the no-history floor and the hook records its own series. `test_commit_msg_hook.py` symlinks the real scripts directory rather than stubbing the gate, so AC1 requires a real directory holding the stub and the citation is gone. The hook carries one literal invocation per boundary so AC3 and AC6 are satisfiable by one file. The roster tests move to `tools/tests/test_boundary_roster.py`, which the census attributes by name; `test_pre_push_hook.py` references `tools/gate_timing.py` (AC4) and the delivery runs `tools/test_census.py` before committing so an unattributed module does not refuse the commit - `test_pre_push_hook.py` must reference the `gate_timing` stem more often than any other `tools/*.py` stem (word-bounded; `gate.py` mentions do not count). The cost ruling is AC9, a decision at plan sign-off, and the hook names `--no-verify` only in the gate refusal, never in BG0642's red-CI refusal.

## Impact

Two lanes this project relies on for release confidence have never run at the boundary they claim. `release-rehearsal` walks greenfield init and a v4 upgrade - the two states the repo cannot occupy - and it was written because walking them by hand once found three consumer-facing defects the whole suite had missed. `revert-check` catches a test that passes without the change it covers. Both are off, and the documentation says otherwise.
