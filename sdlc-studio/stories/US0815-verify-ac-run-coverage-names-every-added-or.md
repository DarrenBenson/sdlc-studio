## User Story

**As a** Maya Okafor
**I want** verify_ac run --coverage names every added or changed line of a unit's Affects that its own verifiers never executed
**So that** a unit is verified before the seat does it - Maya Okafor ships real features through a disciplined lifecycle, not ad-hoc edits, and the seats confirm rather than discover

## Acceptance Criteria

- [ ] **AC1** Given a unit and the run whose APPROVED BATCH names it (read from run-state.json whether that run is open or closed - the ref belongs to the unit's run, and a run whose batch does not name the unit is never read; with no such run, `--base <ref>` is required and its absence refuses naming the flag), when `verify_ac.py run --id <unit> --coverage` runs, then the unit's OWN added lines are the lines added by the commits between that base ref and HEAD whose SUBJECT names the unit id or whose `Refs:` lines name it - the commit-msg hook writes one `Refs: <id>` line per id, and history also holds the older comma-separated single line, so the reader accepts both shapes and parses the message text itself, because git's trailer parser does not see a line above the sign-off block - a commit naming the unit only in body prose is NOT its commit - plus the working tree's uncommitted changes; a line added by another unit's commit in a shared file is not this unit's, the cluster-mate control's commit names the unit under measurement in its BODY prose so the prose-attribution mutant reports it and dies, and a fixture commit names the unit ONLY on `Refs:` lines with an unexecuted added line - several `Refs:` lines with the unit on a LATER one, beside a second commit using the comma form - so a subject-only matcher, or a reader taking the first `Refs:` line alone, misses it and dies; the fixture also seeds a run-state whose batch names a DIFFERENT unit, so a reader that skips the batch-membership check takes its ref and dies - and the report names the file and each of those lines by number that no `Verify:` selector of the unit executes; the same unit with every added line executed by its own selectors reports `uncovered: 0` - the paired control, whose Affects file also carries a PRE-EXISTING line committed at the base ref that no selector executes, so the diff-filter mutant reports that line and dies, and a cluster-mate's commit adding an unexecuted line to the same file, which the attribution mutant reports and dies on.
  - **Verify:** pytest .claude/skills/sdlc-studio/scripts/tests/test_verify_ac.py::LineCoverageTests::test_uncovered_added_lines_are_named_by_number_and_covered_ones_are_not
  - **Verified:** yes (2026-09-08)
- [ ] **AC2** Given an added line that only a test OUTSIDE the unit's own `Verify:` selectors executes - a test in the SAME module as the unit's selector, so a whole-module collection would run it - when the report is produced, then that line is uncovered, because coverage is collected from the unit's own selectors alone; a `shell`, `grep`, `eval` or `http` verifier is listed `not traced` and contributes no coverage, and a Python file whose only selectors are untraced is reported `not measured - no traced verifier` by name rather than as fully uncovered, with the exit code decided by measured files alone (the fixture holds one such file and asserts exit 0).
  - **Verify:** pytest .claude/skills/sdlc-studio/scripts/tests/test_verify_ac.py::LineCoverageTests::test_only_the_units_own_verifiers_count_as_coverage
  - **Verified:** yes (2026-09-08)
- [ ] **AC3** Given the `coverage` module absent - the interpreter that runs the selectors under coverage is `SDLC_COVERAGE_PYTHON` when set, else `sys.executable`, and the absence is detected on THAT interpreter by asking it to import `coverage`; the test points the variable at a wrapper interpreter whose `sitecustomize` hides `coverage` - when `--coverage` runs, then it refuses naming the dependency and exits non-zero, printing the whole sentence `coverage: not measured - the coverage module is absent` (asserted whole, with the non-zero exit, because AC2's per-file line also carries `not measured`), and never reports `uncovered: 0`; a `coverage` older than 7.10, the floor `patch = subprocess` needs, is refused the same way naming the floor - the fixture points the interpreter at a stub `coverage` package whose `__version__` is below the floor.
  - **Verify:** pytest .claude/skills/sdlc-studio/scripts/tests/test_verify_ac.py::LineCoverageTests::test_a_missing_coverage_module_is_refused_not_read_as_covered
  - **Verified:** yes (2026-09-08)
- [ ] **AC4** Given the shipped CLI run as a SUBPROCESS over a fixture unit, when it exits, then the exit code is non-zero with uncovered lines and zero without, and the JSON report written by `--report` carries, under the key `coverage`, the per-file uncovered line list, the base ref, and a content hash over the unit's Affects files at measurement time, so a gate can tell a stale report from a current one; coverage's own data files are written under `sdlc-studio/.local/coverage/` (or a temporary directory), never at the tree root, and the test asserts no `.coverage*` file appears in the fixture root, because the `repo-writes` lane refuses a commit whose hook run created an untracked file.
  - **Verify:** pytest .claude/skills/sdlc-studio/scripts/tests/test_verify_ac.py::LineCoverageTests::test_the_cli_exit_code_and_report_carry_the_verdict
  - **Verified:** yes (2026-09-08)
- [ ] **AC5** Given an Affects file that is not Python (markdown, a shell hook, YAML), when the report is produced, then the file is listed `not measurable`, counted neither covered nor uncovered; the fixture holds the exit-0 control (markdown added lines, every Python line covered) so the exit code is decided by the Python files alone.
  - **Verify:** pytest .claude/skills/sdlc-studio/scripts/tests/test_verify_ac.py::LineCoverageTests::test_a_non_python_affects_file_is_reported_not_measurable
  - **Verified:** yes (2026-09-08)
- [ ] **AC6** Given an added line executed ONLY inside a child interpreter that the unit's own selector spawns (the shipped CLI run as `sys.executable` subprocess, which is how this repository's criteria run by rule), when the report is produced, then that line is covered - coverage follows child processes through `coverage`'s subprocess patching, and the fixture's selector runs the Affects script as a subprocess with a line reachable only there.
  - **Verify:** pytest .claude/skills/sdlc-studio/scripts/tests/test_verify_ac.py::LineCoverageTests::test_a_line_executed_only_in_a_spawned_child_is_covered
  - **Verified:** yes (2026-09-08)
- [ ] **AC7** Given `.github/workflows/lint.yml`, when its `ci` job is read, then `coverage>=7.10` is installed in a step whose POSITION is before the suite step (the test asserts order, not presence - the module is already installed after the suite today), AGENTS.md's soft-dependency table names `coverage` (7.10 or later) beside the feature it serves, and README's dependency sentence no longer says PyYAML is the one optional dependency - the pin exists because the push that ships this story would otherwise turn main red on a runner without the module.
  - **Verify:** pytest tools/tests/test_lint_workflow_coverage.py::CoverageBeforeSuiteTests::test_coverage_is_installed_before_the_suite_runs_and_named_as_a_dependency
  - **Verified:** yes (2026-09-08)
