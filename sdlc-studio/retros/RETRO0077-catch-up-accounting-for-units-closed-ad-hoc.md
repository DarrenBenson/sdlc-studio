# RETRO-0077: Catch-up accounting for units closed ad-hoc before v5 (BG0271, BG0294-0299, EP0161, US0432)

> **Date:** 2026-07-27

> **Goal:** Retrospective accounting for delivery units closed ad-hoc before the v5 close discipline, so the close-owed ledger is honest
> **Delivered:** 9 / 9   **Blocked:** 0

## Delivered

This is a catch-up retro: these units reached terminal in earlier sessions (around the v5 cut) via
direct fixes and commits, before the two-role sprint-close discipline was routine, so no batch retro
accounted for them. Recorded here so the close-owed ledger reflects reality.

- BG0271 - the site-sweep test was unrunnable inside a git worktree (ancestor worktree marker); Superseded.
- BG0294 - duplicate detection had two implementations with different algorithms; unified.
- BG0295 - changelog.py compose folded every pending fragment into [Unreleased]; scoped.
- BG0296 - mutation.py's test-file scan descended into gitignored worktree copies; excluded.
- BG0297 - the two duplicate-detection entry points now share one algorithm and spec.
- BG0298 - resolve_prose_fields checked the wrong set (prose_keys); corrected.
- BG0299 - sprint plan crashed with TypeError on every invocation (Test Levels TSD shape); fixed + forward-deployed.
- EP0161 / US0432 - re-budgeted the pre-commit gate against the ~317s measured peak so a normal commit is not flagged.

## Blocked / deferred

- None. All nine are terminal; this retro only accounts for them.

## What went well

- The fixes themselves were sound and are terminal; the gap was accounting, not delivery.

## What was hard / what stalled

- Units fixed directly during a fast v5 push accumulated as close-owed debt: the close-owed detector rightly kept flagging them until a retro named them. The lesson is to close through a sprint even for a small ad-hoc fix, or accept a periodic catch-up retro like this one.

## Lessons

- A fix committed outside a sprint close is still delivery, and the close-owed ledger will hold it against the next close until a retro accounts for it. Either close small fixes through a sprint, or run a periodic catch-up retro before the ledger grows.

## Estimate vs actual

**Were the estimates any good?** The plan forecast a token cost per unit; telemetry recorded
what each one actually cost. This section holds the comparison, so the question is asked every
sprint instead of only when someone remembers to ask it.

Generate it: `scripts/retro.py accuracy --id RETROxxxx --write` - it fills the block below from
the batch's telemetry and appends this sprint's row to `retros/VELOCITY.md`.

A unit with no per-unit telemetry record has its PER-UNIT ratio reported as **UNMEASURED** and
excluded from that ratio - it is never counted as accurate. But the token count itself is NOT
unmeasurable: the harness tracks it deterministically. An INTERACTIVE sprint (no runner) records no
per-unit actual, so the close captures this RUN's share of the harness-tracked total itself
(`accuracy --tokens-from-harness`, run by `sprint close --apply-signoff`) and the velocity row
records it. The meter is per-SESSION and cumulative, so what is captured is the delta from the
baseline stamped when the run opened - not the session total, which in a session holding more than
one sprint counts the earlier ones again. A run with no baseline (opened before the baseline
existed, or closed from a different session) reports **not-attributable** rather than a number:
there is no fallback to the raw total, because a plausible-looking figure that is not this sprint's
cost is worse than an absent one. When the capture cannot attribute, the close states why and
`accuracy --tokens N` remains the manual override.
Report it as **not-yet-captured** only while neither has happened, never as if the number were
unknowable. That figure is DESCRIPTIVE, never a target (see CR0273).

The forecast is a hypothesis, not a settled calibration. Read the ratio, write down what it
implies, and change the constants only on evidence a human has looked at - a fit to a couple of
sprints fits noise.

This is the question that turns a retro into work. Every finding gets a disposition:
**file it** (a BG/CR id), **record it fixed in-sprint** (`fixed-in: <sha or unit>`), or
**decline it with a reason**. All three are green. What does not pass is silence - a
finding written down and left to rot. The three are counted separately at close: a sprint
that repaired eleven findings reads as eleven fixed, not eleven declined.

To say "nothing worth raising", say so in a row and give the reason. An empty table is
not an answer.

## Close loop (gated)

`gate --require-retro RETROxxxx` (this retro's id, file form) fails until all four are true:

- [ ] this retro exists AND passes its content check - required sections, at least one real
      lesson, and every finding dispositioned (`retro.py validate --id RETROxxxx`)
- [ ] its lessons are in the project store, not just in this file (`retro.py extract --id RETROxxxx`)
- [ ] open lessons re-validated: each is closed, extended, or within its horizon (`lessons revalidate`)
- [ ] `retros/LESSONS-SUMMARY.md` regenerated from the still-valid lessons (`lessons summary`)

The next sprint reads them automatically: `sprint plan` prints the digest in the plan.
