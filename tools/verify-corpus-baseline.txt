# The corpus verification baseline - what the scheduled `corpus-verify` lane tolerates today.
#
# WHY A BASELINE AND NOT A GREEN BAR. `gate.py --release` reports red acceptance criteria across
# stories already at Done. Measured 2026-08-12 at the v5.0.1 close: 52 red of 1,906 across 670 stories in 1,818s.
# The v5.0.0 close recorded 50 of 1,918 across 673 and that reading could NOT be reproduced a day later
# on a tree whose stories are byte-identical - the DENOMINATOR differs, so the two runs were not
# measuring the same set and the gap between their red counts says nothing about regression (D0142). The figure MOVES - it was 106 of 1,824 on 2026-08-07 and 53 of 1,876 on 2026-08-09 - and
# it has been wrong in this repository's own records every time it was carried forward instead of
# re-run - 106, then 53, then 58, and 50 at the tag, with the dead-stamp row moving 5 to 3 in the
# same measurement. That is the argument for the lane, not a footnote to it: a number nobody re-measures is
# a number that is wrong, and this one was out by half once and by five two days later.
# They are stale SELECTORS, not broken features - renamed test methods, deleted test files - and
# D0137 rules the repairs into v5.1 as their own sweep, because a repair that merely makes a
# criterion pass is worse than the red it replaced: it converts a visible stale selector into an
# invisible vacuous one. Each repair has to still discriminate for the criterion it was written
# for, which is review work, not a bulk edit.
#
# So the lane does not demand zero. It demands NO WORSE, and it reddens in BOTH directions:
#   - a count ABOVE the baseline blocks, because that is a new dead selector nobody guarded
#   - a count BELOW the baseline blocks too, because a baseline that only ever tolerates is one
#     that never empties. Lower it in the same commit that fixes the criteria.
#
# The write-time guard is what stops the number climbing: `file_finding.file` and `artifact.py new`
# both refuse a `Verify:` selector naming a node absent from a test file that exists, and a
# mistyped path whose basename exists elsewhere - so these 58 are a closed set being drained
# rather than an open one being fed. What the guard deliberately does NOT refuse is a test file
# not yet written, because that is ordinary test-after-story ordering and every greenfield project.
#
# RE-BASELINED 2026-08-17, 52 -> 20, and the drop is a MEASUREMENT CHANGE rather than 32 repairs.
# The metric is defined above, twice, as red criteria "across stories already at Done". The lane
# counted every story at any status. Measured across 670 stories on the day this row moved: 87 red
# in total, of which 20 sit on stories at Done. The remaining 67 are on Ready, Superseded and
# Won't Implement work - unbuilt or abandoned, never claimed finished - so a criterion failing
# there was never evidence of rot, and the lane's own remedy text was telling readers to hunt them
# as renamed tests. Filed and fixed as BG0592.
#
# THIS IS ALSO WHY THE NUMBER NEVER HELD STILL. The header above records it moving 106, 53, 58, 50,
# 52 and notes a reading that "could NOT be reproduced a day later on a tree whose stories are
# byte-identical - the DENOMINATOR differs". A population containing every un-started story moves
# whenever anybody grooms. A `design` rung makes that unavoidable rather than incidental: its whole
# product is criteria that fail until the code exists, so the metric and the rung were in direct
# conflict - one run of it added 33.
#
# The 68 excluded criteria are still EXECUTED and still reported, on their own line with each
# story's status, so the exclusion is auditable rather than taken on trust.
#
# TWO FALSE READINGS WERE TAKEN BEFORE THIS ONE, and both are recorded because a baseline is
# exactly the place where an unverified number does its damage. The first was 26: an uncommitted
# provenance tag in `gate.py` was failing `lint-style.sh`, and six criteria invoke that lane, so
# the author's own violation was about to be banked into the tolerance for good. The second was a
# per-AC partition reading 21, one higher than the lane. Its extra row was US0031::AC3, which runs
# the whole of `test_gate.py` and TIMED OUT in a 670-story per-AC sweep while passing both alone
# and inside the lane's batched run - so the reading was an artefact of load, and the first
# write-up of it here had the direction of that argument backwards.
#
# A review then found the exclusion FAILING OPEN on any status its literal set did not recognise -
# a decorated `Done (v5.0.1) · **CR:** CR0088` was being excluded - and it now routes through
# `sdlc_md.canonical_status` and `is_delivered_terminal`. Re-measured after that fix: 20 red and 67
# excluded, IDENTICAL to before it. No story in this corpus currently carries a decorated or
# off-vocabulary Done, so the repair is defensive here and had no victims to recover. That is worth
# recording rather than glossing: it is the difference between a fix that changed a number and one
# that closed a route, and only the second is true of it.
#
# 20 is the figure the lane itself produces, by the code path CI runs, on a clean tree. It carries
# one known instability: a timing-sensitive row of that kind flips the count between 20 and 21 if
# it ever lands on a Done story, and this lane blocks in BOTH directions, so that would refuse on
# a coin toss. It was measured on a developer machine; `corpus-verify` in CI installs neither
# ripgrep nor the wider tool set the `ci` job does, so a criterion invoking one could read
# differently there. Both are reasons to re-measure rather than to trust this line twice.
#
# metric|count|what it counts
red-criteria|20|executable acceptance criteria that FAIL when run, across stories already at Done
dead-stamps|3|criteria stamped `Verified: yes` whose selector now selects nothing
